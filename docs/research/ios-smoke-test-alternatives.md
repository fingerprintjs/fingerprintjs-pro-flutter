# Alternatives to the iOS smoke test

Researched on 2026-09-16. These are source-based findings. None of the alternatives has been exercised against this repository in CI.

Follow-up: a [local Maestro trial](../../example/maestro-prototype/README.md) passed five live iOS runs and correctly failed a deliberately wrong ID comparison. The results below distinguish source research from that local experiment.

## Recommendation

For the existing example UI smoke flow, try Maestro on iOS and Android while retaining the current web test. Maestro drives the compiled app through platform accessibility. It does not require a Dart test binding or a VM service connection, so it avoids the two specific mechanisms behind this PR's workarounds. Existing Flutter keys need text selectors or `Semantics(identifier: ...)` wrappers because keys are absent from the platform accessibility tree. This still exercises button handlers, Dart APIs, native plugin registration, platform channels, and the live service. See [Maestro's Flutter documentation](https://docs.maestro.dev/get-started/supported-platform/flutter).

This is a candidate to prove, not a claim that all iOS instability disappears. A prototype should preserve the current assertions, including comparing the ID displayed after identification with `visitorId` in the visitor data dialog. Check the actual accessibility tree for the JSON text before committing to this approach.

If the intended check is only SDK behavior, a normal Flutter application that calls the public SDK methods itself is a smaller alternative. Use `WidgetsFlutterBinding.ensureInitialized()`, initialize the plugin, await the SDK checks, and write a terminal JSON result. On an iOS simulator the host can install and launch the built app with `simctl`, then read its data container. A file result avoids both VM service discovery and ephemeral log capture. Require a fresh run ID, atomic completion, an explicit failure result, and a host timeout so stale files or crashed apps cannot pass. This is an untested design suggestion. It gives up coverage of the example's buttons, state updates, and dialog.

## Smaller changes that do not remove both pitfalls

The official `integration_test` XCTest runner receives results over `plugins.flutter.io/integration_test`. The native runner waits for the plugin's results dictionary and generates native test results from it. Running through `xcodebuild` therefore avoids the Flutter tool's VM service discovery step. Flutter documents a `RunnerTests` unit testing bundle with `INTEGRATION_TEST_IOS_RUNNER(RunnerTests)` and `xcodebuild test-without-building`. However, retaining `testWidgets` retains its end-of-test semantics invariant. See the [native runner source](https://github.com/flutter/flutter/blob/master/packages/integration_test/ios/integration_test/Sources/integration_test/FLTIntegrationTestRunner.m) and [iOS setup instructions](https://github.com/flutter/flutter/blob/master/packages/integration_test/README.md#ios-device-testing).

Changing `testWidgets` to ordinary `test()` is unsafe with that native runner. The integration binding does register `tearDownAll`, but it sends its own `results` map. Successful entries come from its overridden `runTest`; failures come from the Flutter test exception reporter. Ordinary `test()` forwards its body to the test declarer and does not enter either widget test path. A failure can therefore leave the native dictionary empty. The native runner has no empty-dictionary failure check. See [integration binding source](https://github.com/flutter/flutter/blob/master/packages/integration_test/lib/integration_test.dart) and [test compatibility source](https://github.com/flutter/flutter/blob/master/packages/flutter_test/lib/src/test_compat.dart).

A custom API test wrapper could call `binding.runTest(body, () {}, description: name)` inside `test()` and register `binding.postTest` for cleanup. `testWidgets` supplies the semantics check through its invariant callback, so an empty callback removes that check while the binding still records results. This uses a public but lower-level API and requires a pass/fail prototype, native timeout, and nonempty-results guard. It is an untested option, not a drop-in recommendation. See [`runTest` documentation](https://api.flutter.dev/flutter/flutter_test/TestWidgetsFlutterBinding/runTest.html), [`postTest` documentation](https://api.flutter.dev/flutter/flutter_test/TestWidgetsFlutterBinding/postTest.html), and [`testWidgets` source](https://github.com/flutter/flutter/blob/master/packages/flutter_test/lib/src/widget_tester.dart).

The repository currently has only an iOS `Runner` target, with no `RunnerTests`. Adopting the native runner requires a new target and scheme membership. The PR uses SwiftPM in CI, while the README setup describes CocoaPods search paths. Check that the new test target imports and links the SwiftPM `integration_test` product without accidentally switching the app back to CocoaPods.

## Other frameworks

Legacy Flutter Driver runs the app with its driver extension rather than an in-app `testWidgets` test. `requestData` can call an app-supplied handler, and `runUnsynchronized` disables frame synchronization around driver actions. This removes the widget semantics invariant, but still uses the VM service and therefore needs the current explicit connection workaround. It also adds a legacy testing API. See [`enableFlutterDriverExtension`](https://api.flutter.dev/flutter/flutter_driver_extension/enableFlutterDriverExtension.html), [`requestData`](https://api.flutter.dev/flutter/flutter_driver/FlutterDriver/requestData.html), and [`runUnsynchronized`](https://api.flutter.dev/flutter/flutter_driver/FlutterDriver/runUnsynchronized.html).

Patrol uses native XCTest execution and a separate app service for Dart test coordination. However, its `patrolTest` implementation calls `testWidgets`, and its binding inherits `LiveTestWidgetsFlutterBinding` and forwards the invariant callback. Merely migrating the existing flow to Patrol does not remove the semantics check. Its extra native runner and dependencies do not appear justified for this smoke flow. See [Patrol's native execution documentation](https://patrol.leancode.co/documentation/ci/platforms), [`patrolTest` source](https://github.com/leancodepl/patrol/blob/master/packages/patrol/lib/src/common.dart), and [binding source](https://github.com/leancodepl/patrol/blob/master/packages/patrol/lib/src/binding.dart).

Native SDK-only XCTest tests remove Flutter's testing mechanisms but lose coverage of Dart serialization, method names, plugin registration, and real channel communication. Flutter specifically recommends integration tests for platform channel calls. Native plugin tests plus mocked Dart tests can cover each half, but are a different level of assurance. See [Flutter's plugin testing guidance](https://docs.flutter.dev/testing/testing-plugins).

Maestro's current Flutter documentation also describes web support, with an explicit `SemanticsBinding.instance.ensureSemantics()` call required because Flutter's canvas renderer does not enable the accessibility DOM overlay by default. That adds another change to prove. Starting with mobile keeps the existing browser test available during evaluation.

## Verification limits

Inspected the repository's smoke test, driver, simulator script, example app, iOS project, and the installed Flutter source. Local simulator verification was unavailable because Xcode's license has not been accepted. The alternatives still need a real pass, a deliberately failing assertion, an app crash, and repeated CI runs before replacing the current workflow.
